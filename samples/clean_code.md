# 소프트웨어 엔지니어링: 단일 책임 원칙(SRP)과 기술 부채(Technical Debt)

## 1. 단일 책임 원칙 (Single Responsibility Principle, SRP)
SOLID 객체 지향 설계 원칙 중 첫 번째 원칙으로, "하나의 클래스나 모듈은 오직 하나의 변경 이유(Single reason to change)만을 가져야 한다"는 개념이다.

- **문제점 (만능 클래스 / God Object)**: 하나의 파일이나 함수가 데이터베이스 연결, 비즈니스 로직, UI 렌더링, 이메일 발송까지 모두 처리할 경우, 작은 수정 하나가 시스템 전체의 사이드 이펙트(부작용)를 유발한다.
- **해결책**: 데이터 조회 책임, 결제 검증 책임, 알림 발송 책임을 각각 별개의 서비스/클래스로 분리하여 응집도를 높이고 결합도를 낮춘다.
- **실무 교훈**: "이 코드가 바뀌어야 하는 이유가 2가지 이상이라면, 즉시 리팩토링 대상이다."

## 2. 기술 부채 (Technical Debt)
단기적인 빠른 출시를 위해 임시방편(Hardcoding, 테스트 코드 누락, 구조적 결함)으로 작성된 코드는 장기적으로 더 많은 유지보수 비용과 시스템 결함을 초래한다는 금융 비유이다.

- **원리**: 부채를 내서 집을 사듯 빠른 기능 배포는 가능하지만, 원금(리팩토링 비용)과 이자(기능 추가 시 쏟아붓는 버그 수정 시간)가 눈덩이처럼 불어나 결국 개발 속도가 0에 수렴하게 된다.
- **관리 전략**: 스프린트마다 전체 가용 시간의 20%를 '기술 부채 상환(Tech Debt Paydown)'에 배정하고, 테스트 커버리지를 점진적으로 확보해야 한다.
